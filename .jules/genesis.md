## 2024-03-20 — External API Resiliency
**Failure point found:** External API calls to Gemini, DeepSeek, Bhashini, and Ollama were unprotected, meaning any transient network error, rate limit (429), or temporary server error (500) would cause the call to immediately fail and crash the request for the user.
**Why it existed:** Native `fetch` does not have built-in retry mechanisms, and developers assumed API calls would always succeed or fail permanently.
**Recovery built:** Added `fetchWithRetry` wrapper that intercepts 5xx errors, 429s, and network exceptions, applying exponential backoff (100ms, 200ms, 400ms) up to 3 attempts. Safely handles timeouts by recreating `AbortController` signals per attempt. Prevents socket memory leaks by consuming failed response bodies before retrying. Differentiates client aborts (no retry) from internal timeouts (retry).
**Blast radius before:** Any network jitter or third-party service hiccup would return an error to the user immediately, resulting in broken chats and failed audio transriptions.
**Watch for:** Ensure we don't accidentally wrap non-idempotent endpoints (e.g. state-mutating POST requests where the remote server might process it twice) if they don't support idempotency keys. However, the current endpoints (chat completions, STT) are inherently idempotent in terms of impact (no data corruption if double-processed).
